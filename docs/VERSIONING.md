# 提交与版本发布约定

提交信息遵循 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/zh-hans/v1.0.0/)，版本遵循 [SemVer 2.0.0](https://semver.org/lang/zh-CN/)。提交标题使用 `<类型>(<范围>): <中文描述>`；范围可省略。正文说明改动原因、行为和必要的兼容性约束。

## 类型与版本

| 类型 | 用途 | 版本影响 |
| --- | --- | --- |
| `feat` | 新增用户可用能力 | 次版本递增、修订号归零 |
| `fix` | 修正既有行为 | 修订号递增 |
| `perf` | 保持行为的性能优化 | 按是否修正问题决定是否发布修订版 |
| `refactor`、`test`、`docs`、`build`、`ci`、`chore` | 重构、验证、文档及工程维护 | 单独出现时不自动增加功能版本 |
| 任意类型加 `!` 或 `BREAKING CHANGE:` 脚注 | 不兼容变更 | 必须说明影响与迁移方式 |

本项目仍处于 `0.y.z` 开发阶段；不兼容变更通过新的次版本发布并明确标记，不暗中放入修订版。进入 `1.0.0` 前应先确定稳定契约，包括 RON 配置兼容性、CLI 参数与返回码、调度和并发语义。进入稳定版后，不兼容变更提升主版本。

一个版本可以包含多个功能提交及修复，按其中最高级别的变更决定版本增量。发布提交使用 `chore(release): 发布 vX.Y.Z`，只在功能、测试、文档与构建配置准备完成后同步 workspace 版本和锁文件。

## 发布流程

1. 本地及 CI 共用根目录 `rust-toolchain.toml`；更新工具链时同步修正新诊断并完成格式、零警告 Clippy 和全量测试。
2. 每次推送前查询仓库的 Actions，确认没有排队、运行中或等待批准的流水线。先单独推送主分支代码历史，等该次流水线全部成功后，再逐个推送与 Cargo 版本严格一致的 `vX.Y.Z` 标签；每个标签也必须等待上一次流水线结束后才推送。失败时先处理原因，不继续推进后续版本。不将分支与标签放入同一次推送，也不批量推送全部标签。
3. `main` 推送、PR、`v*` 标签推送和手动运行都触发检查、测试与打包。只有标签推送且前置检查全部通过时才执行 GitHub Release 创建，每个发布标签有独立的完整 CI/CD 记录。
4. 检查每个标签的完整流水线及发布资产，不能用主分支的一次成功替代所有版本的验收。
5. 版本发布后保持其代码与标签内容不变。后续修复发布新版本，不移动已发布标签或覆盖同版本的不同程序。

本次仓库重建按用户要求将新发布系列从 `0.1.0` 重新编号。旧系列在本地 Git bundle 与保留的 ngitlab 仓库中归档，不向新 GitHub 仓库混推旧标签。
